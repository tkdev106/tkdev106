戦略的ドメイン駆動設計

在庫と献立のドメインモデル

冷蔵庫の在庫を起点に献立を提案するアプリケーションの、サブドメイン分類・境界づけられたコンテキスト・集約と不変条件。実装時の判断の余地をできるだけ潰すことを目的とする。アーキテクチャ上の決定はアーキテクチャ決定録にある。

01

サブドメインの分類

どこに労力を注ぎ、どこを既製品で済ませるかの判断。献立提案だけがコアドメインであり、在庫管理はその入力を供給する支援に過ぎない。在庫管理そのものを作り込むと、目的（献立を考える手間の解消）から逸れる。

コアドメイン

献立提案

在庫を制約として献立を生み、提示し、記憶する。差別化の源泉であり、設計とテストの投資先。

支援サブドメイン

在庫管理

コアへの入力を供給する。汎用品では代替できないが、それ自体は価値を生まない。素朴に作る。

汎用サブドメイン

食材カタログ

食材名の正規化・別名・カテゴリ。既製のデータで代替可能。自作しない。

汎用サブドメイン

アカウント・世帯

認証と世帯の識別。外部の認証基盤に委譲し、自前で持つのは世帯の識別子のみ。

02

境界づけられたコンテキストとコンテキストマップ

4つのコンテキストに分ける。MVP では単一デプロイのモジュラーモノリスとして実装し、コンテキスト間はモジュール境界として表現する（ADR-004）。

腐敗防止層（ACL）が守るもの

LLM は形式の揺れた出力を返しうる。ACL は「LLM の応答 JSON」を「MealIdea のドメインオブジェクト」に変換し、変換に失敗したものはドメイン層に一切渡さない。ドメイン層のどこにも、LLM・プロンプト・JSON という語が現れてはならない。

03

ユビキタス言語（暫定）

日本語の語と、コード上の識別子を1対1で固定する。この表にない語をコードに登場させない。「レシピ」「メニュー」「候補」といった同義語の混在が、AI 実装で最も曖昧性を生む。用語は別途調整するため暫定とする。

04

集約と不変条件

集約ルートは4つ。集約をまたぐ参照はすべて識別子で行い、オブジェクト参照を持たない（ADR-008）。1トランザクションで更新してよいのは1集約まで。

コア献立案MealIdea

構成

  • id: MealIdeaId
  • householdId: HouseholdId
  • title: string — 献立の名称
  • ingredients: MealIngredient[] 値オブジェクト
  • steps: CookingStep[] 値オブジェクト
  • provenance: 'llm' — 生成元
  • generatedAt: DateTime
  • cookingRecords: CookingRecord[]

不変条件

  • title は空文字を許さない
  • ingredients は1件以上
  • steps は1件以上、順序を持つ
  • ちょうど1つの世帯に属し、所属は変わらない
  • cookingRecords は追加のみ。削除・更新しない
  • 生成後、title／ingredients／steps は不変
コア提案Suggestion

構成

  • id: SuggestionId
  • householdId: HouseholdId
  • mealIdeaIds: MealIdeaId[] — ID 参照
  • pantrySnapshot: PantrySnapshot 値オブジェクト
  • generatedAt: DateTime

不変条件

  • mealIdeaIds はちょうど3件
  • 参照する献立案は同じ世帯に属する
  • 生成後は完全に不変（追記も削除もしない）
  • pantrySnapshot は生成時点の複製であり、以後の在庫変更を反映しない
在庫品StockItem

構成

  • id: StockItemId
  • householdId: HouseholdId
  • name: string — 自由入力を許す
  • ingredientId: IngredientId | null — カタログに一致した場合のみ
  • amount: Amount | null
  • expiryDate: ExpiryDate | null

不変条件

  • name は空文字を許さない
  • 同じ食材でも統合しない。買った日が違えば別の在庫品（ADR-007）
  • expiryDate が未設定の在庫品は、期限による警告・優先の対象外
  • 削除は物理削除でよい。献立案は材料を複製済みで参照を持たない
食材Ingredientカタログ

構成

  • id: IngredientId
  • canonicalName: string
  • aliases: string[]
  • category: IngredientCategory

不変条件

  • 読み取り専用。アプリケーションから更新しない
  • canonicalName は全体で一意

ドメインサービスとポート

ドメインサービス

MealCoverageService

献立案と現在の在庫品リストを受け取り、賄える材料と不足する材料を返す。純粋関数であり、副作用も永続化も持たない。

ポート（インターフェース）

MealIdeaGenerator

在庫スナップショットを受け取り、献立案3件を返す。ドメイン層に定義し、インフラ層が LLM で実装する。依存の向きが逆転する要（ADR-002）。

05

献立案の状態 —「見た」と「つくった」

「以前見た献立」と「以前つくった献立」を別のフラグとして持たない。調理記録の有無から導出する。状態を二重に持つと必ず食い違うため、単一の事実（調理記録）だけを保存する。

06

曖昧性を排除するための確定事項

実装時に判断を求められそうな箇所を、あらかじめ潰しておく。ここに書かれていることは実装者（AI を含む）が勝手に変えてよいものではない。

C-1　生成した献立案は必ず永続化する

LLM の応答を画面に出すだけで捨ててはならない。ACL で MealIdea に変換した時点で保存する。保存に失敗した献立案は、ユーザーに提示しない。

C-2　生成した3件はすべて提示する

生成件数と提示件数は常に等しい。「生成したが見せていない献立案」は存在しない。これにより提示済みフラグが不要になる。

C-3　献立案は生成後に編集できない

名称・材料・手順は不変。ユーザーが手を加えたい場合の要件は MVP に存在しない。追加されるのは調理記録のみ。

C-4　同じ内容の献立案を重複排除しない

「豚こまと白菜の中華炒め」が別の日に再度生成されても、別の MealIdea として保存する。意味的な同一性判定は MVP では行わない。名称の完全一致による抑制も行わない。

C-5　材料は在庫品を参照せず、文字列として複製する

MealIngredient は StockItemId を持たない。在庫品が削除されても献立案は壊れない。充足判定は名称の突き合わせで都度行う。

C-6　充足判定は名称の完全一致で行う（MVP）

「豚こま肉」と「豚こま」は一致しないものとして扱う。表記ゆれの吸収は食材カタログの別名機能に委ね、それでも漏れるものは不足材料として表示する。これは既知の割り切りであり、精度の問題が出たときに見直す。

C-7　再生成の判定は在庫スナップショットの一致で行う

最新の Suggestion.pantrySnapshot が現在の在庫と一致する場合、生成 API を呼ばず保存済みの献立案を返す。一致判定は在庫品の (name, amount, expiryDate) の集合比較とする。id は比較に含めない。

C-8　調理記録は在庫を自動で減らさない

「作った」を記録しても在庫品は自動削除されない。何をどれだけ使ったかを正しく推定できないため。在庫の消費はユーザーが在庫画面で明示的に行う。

C-9　世帯 ID はすべての集約が保持する

4つの集約ルートすべてが householdId を持ち、リポジトリの全メソッドは householdId を必須引数に取る。世帯をまたぐ取得を、型として不可能にする。

#論点影響
Q-1ユビキタス言語の最終決定。特に MealIdea の日本語（献立案 / 献立 / お品書き）と、UI 上の「以前見た献立」の呼び方。全レイヤーの命名。実装開始前に確定させる必要がある。
Q-2献立案の保持期間。無制限に貯めるか、一定期間で削除するか。ストレージ費用と、履歴一覧の設計。
Q-3提案が3件固定でよいか。在庫が少ないときに3件出せない場合の扱い。Suggestion の不変条件。現状は「ちょうど3件」としている。
Q-4食材カタログの初期データの出所と件数。C-6 の充足判定の精度に直結する。
