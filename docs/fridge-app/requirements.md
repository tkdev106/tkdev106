## 1. 背景と課題

家庭の食材管理は、以下の理由で「買ったのに使い切れない」「あるのに買ってしまう」が発生しやすい。

- 冷蔵庫の中身は**開けないと分からない**ため、買い物中に在庫を思い出せない。
- 奥にしまった食材は視界に入らず、**賞味期限切れに気づくのが遅れる**。
- 「何を作るか」を決めてから食材を探すため、**在庫起点の発想になりにくい**。

在庫管理アプリ単体では「記録が面倒なわりに得るものが少なく」続かない。本アプリは、**記録の見返り＝献立提案**をセットで提供することで、記録を続ける動機を作る。

## 2. 目的とゴール

### 2.1 プロダクトゴール

冷蔵庫の在庫を登録・管理でき、**その在庫を起点に「今日の献立候補」を提示する**ことで、食材の使い切りと献立決めの負担軽減を実現する。

### 2.2 成功指標（KGI/KPI 案）

| 区分 | 指標 | 目標値（初期仮説） |
| --- | --- | --- |
| KGI | 廃棄した食材の件数／月（ユーザー自己申告） | 導入前比で減少 |
| KPI | 週次継続率（週1回以上の在庫更新） | 40% |
| KPI | 献立サジェストの採用率（提示→「作った」記録） | 20% |
| KPI | 食材1件あたりの登録所要時間 | 10秒以内 |

> 注: KPI の目標値は根拠のある実測値ではなく、レビューのたたき台としての初期仮説である。リリース後の実測で更新する。

### 2.3 やらないこと（Non-Goals）

MVP では以下をスコープ外とする。誤解を避けるため明示する。

- 栄養計算・カロリー管理・健康アドバイス
- 買い物リストの自動生成、ネットスーパー連携、価格比較
- 家族間でのリアルタイム共有（→ 将来対応。第10章）
- レシピの投稿・共有などのコミュニティ機能
- 冷蔵庫内カメラ・IoT 機器との連携

## 3. スコープと利用者

### 3.1 対象ユーザー

**MVP: 個人利用（1ユーザー = 1冷蔵庫）**。ただし将来の家族共有を見据え、**データモデルは最初から共有可能な形で設計する**（第8章）。

#### ペルソナ

| 項目 | 内容 |
| --- | --- |
| 名前 | 30代・共働き会社員 |
| 状況 | 平日は帰宅が20時前後。週末にまとめ買いをする |
| 課題 | 週末に買った食材を平日に使い切れず、週の後半に傷ませる。疲れて帰宅すると献立を考える気力がない |
| 期待 | 冷蔵庫を開ける前に中身が分かり、「今日はこれが作れる」を提示してほしい |

### 3.2 対応環境

- スマートフォンのブラウザを主用途とする **レスポンシブ Web アプリ**。
- 台所での片手操作を想定し、モバイルファーストで設計する。
- ネイティブアプリ／オフライン完全対応は MVP スコープ外。

## 4. 用語定義

| 用語 | 定義 |
| --- | --- |
| 食材（Ingredient） | 「にんじん」「豚こま肉」などの**種類**を表すマスタ上の概念 |
| 在庫（StockItem） | ユーザーの冷蔵庫にある**個々の実体**。食材を参照し、数量・期限・保存場所を持つ |
| レシピ（Recipe） | 料理の作り方。必要な食材（材料）の一覧を持つ |
| 献立候補（Suggestion） | 在庫を元にスコアリングされ、ユーザーに提示されたレシピ |
| 期限 | 賞味期限・消費期限を区別せず、単一の「使い切りたい日」として扱う（MVP） |
| 使い切り | 在庫の数量が0になる、または「使った」操作で在庫が消費されること |

## 5. 機能要件

優先度は MoSCoW（Must / Should / Could）で示す。**Must が MVP のリリース範囲**である。

### 5.1 食材の登録・管理

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-01 | 食材を**手入力**で登録できる。入力項目は「食材名（必須）」「数量＋単位」「期限」「保存場所」「メモ」 | Must |
| FR-02 | 食材名は入力途中で**サジェスト（インクリメンタル補完）**され、マスタから選択できる | Must |
| FR-03 | マスタにない食材名は、そのまま自由入力で登録できる（登録がブロックされない） | Must |
| FR-04 | 在庫を一覧表示できる。既定は**期限が近い順**でソートする | Must |
| FR-05 | 在庫の数量・期限・保存場所を編集できる | Must |
| FR-06 | 在庫を削除できる。削除時は「使い切った」「捨てた」を選択でき、後者は廃棄として記録される | Must |
| FR-07 | 保存場所（冷蔵/冷凍/野菜室/常温）で在庫を絞り込める | Should |
| FR-08 | 在庫をカテゴリ（肉・魚・野菜・調味料など）で絞り込める | Should |
| FR-09 | よく使う食材をテンプレートとして保存し、ワンタップで登録できる | Could |
| FR-10 | 複数の食材をまとめて1画面で連続登録できる（買い物後の一括入力） | Should |

**FR-06 の意図**: 「使い切った」と「捨てた」を分けて記録することが、2.2 の廃棄削減 KGI を測る唯一のデータソースになる。単なる削除にしてはならない。

### 5.2 期限管理

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-11 | 期限までの残日数を在庫一覧に表示する | Must |
| FR-12 | 期限が近い在庫を視覚的に区別する（例: 3日以内=警告、当日/超過=危険） | Must |
| FR-13 | 期限切れ間近の在庫をまとめて確認できる画面またはセクションを持つ | Should |
| FR-14 | 期限が近い食材について通知（プッシュ／メール）を送る | Could |
| FR-15 | 期限は任意入力とし、未入力でも登録できる。未入力の在庫は期限による警告対象外とする | Must |

**FR-15 の意図**: 期限を必須にすると登録が面倒になり、2.2 の「10秒以内」と継続率を損なう。記録の心理的コストを最優先する。

### 5.3 献立サジェスト

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-16 | 現在の在庫を元に、献立候補を**複数件**提示できる | Must |
| FR-17 | 各候補について「在庫でまかなえる材料」と「不足している材料」を区別して表示する | Must |
| FR-18 | 候補は**期限が近い在庫を優先的に使うもの**が上位に来るよう並べ替えられる | Must |
| FR-19 | 候補から実際に作った献立を「作った」として記録でき、使用した在庫を消費として反映できる | Should |
| FR-20 | 「不足材料が0件のもののみ」に絞り込める | Should |
| FR-21 | 特定の在庫を指定して「これを使うレシピ」を検索できる | Should |
| FR-22 | サジェストの根拠（なぜこの候補か）をユーザーに提示する | Should |
| FR-23 | 提示された候補に「興味なし」を指定でき、以降のサジェストに反映される | Could |

**FR-22 の意図**: サジェストの実装方式によらず、ユーザーが結果を信頼できるかどうかは「根拠が見えるか」に強く依存する。第6章の方式比較でもこの点を評価軸に含める。

### 5.4 アカウント・認証

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-24 | ユーザーはアカウントを作成し、ログイン／ログアウトできる | Must |
| FR-25 | 在庫データはユーザーごとに分離され、他ユーザーから参照できない | Must |
| FR-26 | ユーザーは自分のアカウントとデータを削除できる | Must |

## 6. 献立サジェスト方式の比較検討【要決定】

本章は**結論ではなく判断材料**である。FR-16〜FR-23 をどう実現するかは、以下の比較を踏まえて意思決定する。

### 6.1 前提となる制約: 日本語レシピの「材料検索」は容易ではない

在庫起点のサジェストの中核は「**材料の集合からレシピを引く**」検索である。ここに構造的な制約がある。

- **楽天レシピAPI** は、公開されているのが「カテゴリ別ランキングAPI」と「カテゴリ一覧API」の2種類で、**材料名を投げてレシピを引く仕様になっていない**。またカテゴリ別ランキングは1リクエストあたりの取得件数にも制限がある。材料検索を行うには、取得したデータを自前のデータベースに蓄積して索引を張る等の追加設計が必要になる。
- **クックパッド**は、一般開発者向けの公開レシピ検索APIを提供していることが確認できなかった。前提にはできない。
- **Spoonacular**（英語圏）は `findByIngredients` という**まさに用途に合う**エンドポイントを持つ。ただしレシピが英語圏の料理中心であり、無料枠はリクエスト数ではなく**ポイント制**（無料枠は1日あたり150ポイント程度、エンドポイントごとに消費ポイントが異なる）。日本の家庭料理アプリとしての妥当性と、コスト設計の両方に懸念が残る。

> つまり「外部レシピAPIを叩けば材料検索ができる」という素朴な前提は、日本語圏では成立しない。方式選定はこの制約を出発点にする必要がある。

### 6.2 方式の選択肢

#### 案A: 外部レシピAPI + 自前スコアリング

外部APIからレシピを取得し、在庫との一致率・期限の近さで自前に並べ替える。

- 6.1 の通り、日本語圏では**材料検索できるAPIが実質見当たらない**ため、素直には成立しない。
- 成立させるには「APIから取得したレシピを自前DBに蓄積し、材料で索引を張る」＝実質的に案Cへ移行する。
- 各APIの利用規約（データの保存・キャッシュ可否、表示義務、アフィリエイト要件）の確認が**必須**。規約違反はサービス停止リスクに直結する。

#### 案B: LLM（Claude API 等）で献立を生成

在庫リストをプロンプトとして渡し、献立と作り方を生成させる。

| 観点 | 評価 |
| --- | --- |
| 初期構築コスト | **低**。レシピDBの構築が不要で、MVPを最短で立ち上げられる |
| 柔軟性 | **高**。「余り物3つ」のような中途半端な在庫でも何らかの提案が出る。材料検索の制約を受けない |
| 日本語・和食対応 | **良好** |
| ランニングコスト | 呼び出しごとに費用が発生。ユーザー数に比例して増える |
| 応答時間 | 数秒かかる。UI 側でローディング体験の設計が必要 |
| 再現性 | 同じ在庫でも毎回異なる結果になりうる。「昨日見た候補が消える」体験を招く |
| 信頼性 | **要注意**。存在しない分量・手順を生成しうる。調理は誤りが実害（食中毒・失敗）につながる領域である |
| 根拠提示（FR-22） | 「なぜこの候補か」を生成文として出せるが、それ自体が生成物であり検証されていない |

#### 案C: 自前レシピDB + マッチングロジック

レシピを自分でデータベース化し、材料の集合演算でマッチングする。

| 観点 | 評価 |
| --- | --- |
| 初期構築コスト | **高**。レシピの初期投入が最大の課題。数十件では提案が貧弱になり、体験が成立しない |
| ランニングコスト | **ほぼゼロ**。外部依存なし |
| 応答時間 | **高速**。DBクエリのみ |
| 再現性 | **完全**。同じ在庫なら同じ結果 |
| 信頼性 | **高**。提示するのは登録済みの検証されたレシピのみ |
| 根拠提示（FR-22） | **容易**。一致した材料をそのまま根拠として示せる |
| 外部規約リスク | なし |

#### 案D: ハイブリッド（案C を基本、案B で補完）

自前DBでマッチングし、候補が閾値未満のときのみ LLM で提案を補う。

- 体験としては最良。日常的には高速・低コスト・高信頼で、在庫が中途半端なときだけ柔軟性を得られる。
- ただし**2系統の実装と、2種類の結果を1つのUIに統合する設計**が必要で、MVP としては明確に重い。

### 6.4 推奨と、決定に必要な問い

**推奨: 案B で MVP を出し、案D へ育てる。**

理由は、本アプリの最大のリスクが「サジェストの精度」ではなく「**そもそも在庫を登録し続けてもらえるか**」にあるためである。案C はレシピDBの初期投入という重い作業を、その検証の**前**に要求する。案B なら在庫登録の継続性を先に検証でき、そこで得た「実際にどんな在庫でどんな提案が求められたか」のログが、案D で作るべきレシピDBの設計根拠になる。

ただし案B を選ぶ場合、**信頼性の担保を要件として明記すること**を条件とする。

- 生成された献立には「AIによる提案です。分量・加熱時間は必ずご自身で確認してください」に相当する注意表示を必須とする（→ FR-27 として第5章に追加要）。
- 生成結果は保存し、同じ在庫に対して短時間で再生成しない（再現性の欠如を UI で緩和する）。
- 生成コストの上限（1ユーザーあたりの1日の呼び出し回数上限）を設ける。

**決定のために回答が必要な問い:**

1. ランニングコストの許容額はいくらか（個人開発の趣味プロジェクトか、将来的な公開・収益化を視野に入れるか）。
2. 「毎回違う献立が出る」ことは、この体験において魅力か欠陥か。
3. レシピの初期データを自分で用意する工数を、どの程度かけられるか。

## 8. データモデル（概念レベル）

技術非依存の概念モデルとして記述する。物理設計は設計フェーズで行う。

```
User ──< Membership >── Household ──< StockItem >── Ingredient
                                          │
                                     Location（冷蔵/冷凍/野菜室/常温）

Recipe ──< RecipeIngredient >── Ingredient
CookingLog ── Recipe, Household
```

### 8.1 主要エンティティ

| エンティティ | 主な属性 | 備考 |
| --- | --- | --- |
| User | id, email, 表示名 | 認証主体 |
| **Household** | id, 名称 | **冷蔵庫の単位**。MVPではユーザー作成時に1件自動生成し、UI上は存在を見せない |
| **Membership** | user_id, household_id, ロール | MVPでは常に1件（owner）。将来の共有はここに行を足すだけで済む |
| Ingredient | id, 正規名, カテゴリ, 別名リスト | 食材マスタ。FR-02 のサジェスト元 |
| StockItem | id, household_id, ingredient_id, 食材名（自由入力用）, 数量, 単位, 期限, 保存場所, メモ | 在庫の実体 |
| ConsumptionLog | stock_item_id, 種別（使い切り/廃棄）, 日時, 数量 | FR-06。KGI 測定の基礎データ |
| Recipe | id, 名称, 手順, 出典（自前/LLM生成/外部API） | 6章の方式により中身は変わるが、**器としては共通** |
| RecipeIngredient | recipe_id, ingredient_id, 分量, 必須フラグ | 案C/D で必要 |
| CookingLog | household_id, recipe_id, 日時 | FR-19。KPI（採用率）測定に使う |

### 8.2 設計上の要点

- **Household / Membership を MVP から入れる**ことが本設計の要点である。ユーザーの回答（「個人利用から始めて共有は将来対応」）に対し、在庫を `user_id` に直接ぶら下げると、共有対応時に全テーブルと全クエリの改修が必要になる。1段のインダイレクションを最初に払っておけば、将来の共有は Membership への行追加とアクセス制御の追加で済む。
- **`Ingredient` と `StockItem.食材名` の二重持ち**は意図的な設計である。FR-03（マスタにない食材も登録できる）を満たすため、マスタ未登録の食材は自由入力の文字列として保持し、後からマスタに紐付けられるようにする。マスタへの完全正規化を強制すると登録がブロックされ、FR-03 と衝突する。
- `Recipe` の出典を属性として持たせることで、第6章の方式決定を**データモデルの決定から切り離す**。案B で始めて案D へ移行しても、スキーマの作り直しは発生しない。

## 9. 非機能要件

技術スタックが未定のため、実装手段ではなく**満たすべき性質**として記述する。

### 9.1 性能

| ID | 要件 |
| --- | --- |
| NFR-01 | 在庫一覧の初期表示は、在庫100件までで2秒以内（モバイル回線を想定） |
| NFR-02 | 食材登録の保存操作は1秒以内に完了応答を返す |
| NFR-03 | 献立サジェストは、処理に3秒以上かかる場合、進行中であることを明示するUIを表示する |

### 9.2 可用性・信頼性

| ID | 要件 |
| --- | --- |
| NFR-04 | 在庫データは日次でバックアップされ、障害時に復旧できる |
| NFR-05 | 外部サービス（レシピAPI / LLM API）の障害時も、**在庫の登録・閲覧は継続して利用できる**。サジェスト機能のみ縮退する |

**NFR-05 の意図**: 在庫管理はこのアプリの土台であり、サジェストの障害に巻き込まれてはならない。方式によらず、サジェスト部分は疎結合に設計する。

### 9.3 セキュリティ・プライバシー

| ID | 要件 |
| --- | --- |
| NFR-06 | 通信は全て暗号化する |
| NFR-07 | 認可はサーバ側で強制する。他ユーザー（他 Household）のデータには、URL を直接指定しても到達できない |
| NFR-08 | パスワードを自前で保持する場合、平文で保存しない。外部の認証基盤に委譲する場合はこの限りでない |
| NFR-09 | LLM を利用する場合、送信するのは在庫の食材名・数量・期限に限定し、ユーザーの氏名・メールアドレス等の識別情報を含めない |
| NFR-10 | FR-26 のアカウント削除時、関連する在庫・ログを削除する |

**NFR-09 の意図**: 食生活は生活実態を推測できる情報である。第6章で案B/Dを選ぶ場合、外部送信の範囲を要件として固定しておく。

### 9.4 ユーザビリティ

| ID | 要件 |
| --- | --- |
| NFR-11 | 主要操作（在庫の登録・編集・削除）は片手で完結できるレイアウトとする |
| NFR-12 | 食材1件の登録は、名前入力から保存まで**10秒以内**で完了できる（2.2 の KPI と対応） |
| NFR-13 | 主要画面は WCAG 2.1 レベル AA 相当のコントラスト比を満たす |
| NFR-14 | 期限の警告は色のみで表現せず、テキストまたはアイコンを併用する |

### 9.5 保守性

| --- | --- |
| NFR-15 | 献立サジェストのロジックは、第6章の方式を差し替え可能なインターフェースの背後に置く |
